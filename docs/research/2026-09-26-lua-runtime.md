# Lua runtime for Sky.Scripting (research, 2026-09-26)

All sources below were retrieved on 2026-09-26 unless a row says otherwise. Repo statistics come from the GitHub REST API (`gh api repos/<owner>/<repo>`, `/releases`, `/commits`, `/contributors`, `search/issues`), package facts from the NuGet v3 registration and flat-container APIs (`api.nuget.org`), and code facts from the source files linked at `main`/`master` on that date. Nothing here was benchmarked by this project; every performance figure is a third party's, and anything without a figure is marked unmeasured.

## Summary

For the M0 boundary spike, benchmark **(1) Lua-CSharp (`LuaCSharp` 0.5.7, nuskey8/Lua-CSharp)** and **(2) MoonSharp 3.0.0-beta.1 (moonsharp-devs/moonsharp)** against plain C# scoring. Lua-CSharp ranks first: it is pure managed code with a `net10.0` target in the package, MIT, the most active of the candidates (a release on 2026-09-26 and 47 PRs merged in the last six months), exposes C# types through a source generator instead of reflection, has a public count hook and per-chunk environments for sandboxing, and its own (2024, pre-rewrite) benchmark shows it allocating about 400x less than MoonSharp or NLua on C# calls. Its costs are Lua 5.2 semantics (doubles only, no integer subtype, and the maintainer says 5.3/5.4 is unlikely), a pre-1.0 API, and a count hook that a user measured at 3.16x on a tight loop. MoonSharp ranks second because it is the other pure-managed option with deterministic insertion-ordered table iteration, built-in sandbox presets and an instruction-count auto-yield, and it came back to life in 2026 (58 commits from 16 authors since 2026-01-01, a 3.0 beta); its costs are a netstandard2.0-only package, reflection-based interop that is not trim/AOT friendly, and heavy allocation per C# call. The native option, **KeraLua** (Lua 5.4.9, MIT, win-x64 and linux-x64 binaries shipped), is the reference VM and the only one with a real memory cap, but it is held back to third because three things work against this project: Lua 5.4 randomizes string hashes per state from time and addresses, so `pairs` order is not reproducible across runs without a custom native build; `lua_error` longjmps over managed frames, which .NET does not support on Linux (CI) and which has open NLua crash reports there; and native libraries from NuGet have a history of load failures under Godot .NET. NLua on top of KeraLua adds reflection proxies and a `luanet` global that can import any CLR type, and is not recommended for sandboxed content. NeoLua, NuLua, NovaSharp, Lua.NET and LuauInterop are recorded below and not recommended for the spike.

## Candidates

### 1. Lua-CSharp (`LuaCSharp` on NuGet)

Maintenance. Repo [nuskey8/Lua-CSharp](https://github.com/nuskey8/Lua-CSharp) (formerly AnnulusGames/Lua-CSharp, per the v0.4.x release links), MIT, 856 stars, last push 2026-09-26. Release [v0.5.7](https://github.com/nuskey8/Lua-CSharp/releases/tag/v0.5.7) was published 2026-09-26; v0.5.6 on 2026-07-29; v0.5.4/0.5.5 on 2026-05-09. The two main committers are akeit0 (479 commits) and nuskey8 (444), with ashtonmeuser (29) a regular contributor; 11 authors committed in 2026. 41 open issues, 4 open PRs, 47 PRs merged since 2026-03-26 (GitHub search API). v0.5.0 (2025-11-21) was a VM rewrite: "The virtual machine implementation has been completely redesigned to provide higher performance and better compatibility with Lua 5.2" ([release notes](https://github.com/nuskey8/Lua-CSharp/releases/tag/v0.5.0)). The package is still 0.x; APIs were renamed in 0.5.0 (for example PRs #179, #180 in those notes).

Platform. The 0.5.7 nuspec lists `net10.0`, `net8.0`, `net6.0` and `.NETStandard2.1` groups, with `lib/net10.0/Lua.dll` in the package and dependencies `LuaCSharp.Annotations` and `LuaCSharp.SourceGenerator` ([nuget.org/packages/LuaCSharp](https://www.nuget.org/packages/LuaCSharp), nupkg from `api.nuget.org/v3-flatcontainer/luacsharp/0.5.7/`). No native binaries. `src/Lua/Lua.csproj` declares `net10.0; net8.0; net6.0; netstandard2.1` ([Lua.csproj](https://github.com/nuskey8/Lua-CSharp/blob/main/src/Lua/Lua.csproj)); it does not set `IsAotCompatible` or `IsTrimmable`. The README says "it operates reliably in AOT environments since it does not rely on IL generation" ([README](https://github.com/nuskey8/Lua-CSharp/blob/main/README.md)). v0.4.0 fixed "floating number not able to be parsed (Godot)" (PR #47, [v0.4.0 notes](https://github.com/nuskey8/Lua-CSharp/releases/tag/v0.4.0)), so it has had at least one Godot user.

Language. "Lua 5.2 interpreter implemented in C#" ([README](https://github.com/nuskey8/Lua-CSharp/blob/main/README.md)). Lua `number` maps to C# `double` (README type table), so there is no integer subtype. `goto` and labels exist (`GotoStatementNode.cs`, `LabelStatementNode.cs` in [src/Lua/CodeAnalysis/Syntax/Nodes](https://github.com/nuskey8/Lua-CSharp/tree/main/src/Lua/CodeAnalysis/Syntax/Nodes)); coroutines are supported and awaitable from C# (README "Coroutines"). Strings are UTF-16, so `string.len("あいうえお")` is 5, not 15 (README "Compatibility"). Issue [#25](https://github.com/nuskey8/Lua-CSharp/issues/25) asks for 5.3/5.4; nuskey8 replied on 2026-06-29 that "adding support for additional versions would likely be quite difficult".

Sandboxing. Libraries are opened one at a time (`OpenBasicLibrary`, `OpenMathLibrary`, `OpenStringLibrary`, `OpenTableLibrary`, `OpenCoroutineLibrary`, `OpenIOLibrary`, `OpenOperatingSystemLibrary`, `OpenModuleLibrary`, `OpenDebugLibrary`, ...) in [OpenLibsExtensions.cs](https://github.com/nuskey8/Lua-CSharp/blob/main/src/Lua/Standard/OpenLibsExtensions.cs), so io, os, package/require and debug are left out by not opening them. The basic library still registers `dofile`, `loadfile` and `load` ([BasicLibrary.cs](https://github.com/nuskey8/Lua-CSharp/blob/main/src/Lua/Standard/BasicLibrary.cs) lines 34-55), so the host must remove them after opening it. `LuaState.Load(chunk, chunkName, LuaTable? environment)` takes a per-chunk environment ([LuaState.cs](https://github.com/nuskey8/Lua-CSharp/blob/main/src/Lua/LuaState.cs) around line 505), which gives each event script its own whitelist table. `LuaPlatform` abstracts the file system, OS environment, stdio and `TimeProvider` (README "LuaPlatform"). Instruction limit: `public void SetHook(LuaFunction? hook, string mask, int count = 0)` ([LuaState.cs](https://github.com/nuskey8/Lua-CSharp/blob/main/src/Lua/LuaState.cs) line 373) supports count hooks, and a hook that throws ends the run. A `CancellationToken` also stops infinite loops (PR [#147](https://github.com/nuskey8/Lua-CSharp/pull/147), merged 2025-05-15, demonstrates a `goto` loop cancelled after 100 ms), but that is wall-clock and not deterministic. Issue [#338](https://github.com/nuskey8/Lua-CSharp/issues/338) (open, 2026-07-31) measured the count hook on v0.5.6, .NET 8, Windows 11: a 2,000,000-iteration loop took 22 ms without a hook and 72 ms with an empty hook at `count = 4` (3.16x, about 49 ns a fire). No memory limit exists: the runtime uses the .NET GC and `collectgarbage` "simply calls the corresponding .NET garbage collection method" (README "Garbage Collection"). Errors: runtime errors throw `LuaRuntimeException`, compile errors `LuaCompileException`, cancellation `LuaCanceledException` (README "Exception Handling"), so a per-script `try/catch` disables one definition. Stack overflow handling is still an open issue ([#168](https://github.com/nuskey8/Lua-CSharp/issues/168)); v0.5.4 added "Throw stack overflow" (PR #276, [v0.5.4 notes](https://github.com/nuskey8/Lua-CSharp/releases/tag/v0.5.4)). `LuaState` "is not thread-safe" (README).

Determinism. `OpenMathLibrary` seeds `math.random` with `new Random()` (unseeded) and stores it in the global environment under the key `__lua_mathematics_library_random_instance` ([OpenLibsExtensions.cs](https://github.com/nuskey8/Lua-CSharp/blob/main/src/Lua/Standard/OpenLibsExtensions.cs) lines 68-86, [MathematicsLibrary.cs](https://github.com/nuskey8/Lua-CSharp/blob/main/src/Lua/Standard/MathematicsLibrary.cs) lines 267-316); `math.randomseed` builds `new Random((int)BitConverter.DoubleToInt64Bits(seed))`. The host must replace `math.random`/`math.randomseed` with functions bound to the engine's named RNG stream, and must not expose the global table itself (the random instance is reachable through it). Table iteration: `LuaTable.TryGetNext` walks the array part and then `LuaValueDictionary`'s entries array ([LuaTable.cs](https://github.com/nuskey8/Lua-CSharp/blob/main/src/Lua/LuaTable.cs) line 215), and entry slots are assigned in insertion order with a hash-independent free list ([LuaValueDictionary.cs](https://github.com/nuskey8/Lua-CSharp/blob/main/src/Lua/Internal/LuaValueDictionary.cs)); string keys hash with `string.GetHashCode()` ([LuaValue.cs](https://github.com/nuskey8/Lua-CSharp/blob/main/src/Lua/LuaValue.cs) line 598), which .NET randomizes per process, but that affects bucket placement, not the order of the entries array. So `pairs` order should follow the sequence of inserts and removes; this is read from source and unmeasured. Floats are C# `double`; transcendental functions go through `System.Math`, which "calls into the underlying C runtime, and the exact result or valid input range may differ between different operating systems or architectures" ([dotnet-api-docs Math.xml](https://github.com/dotnet/dotnet-api-docs/blob/main/xml/System/Math.xml), for example the `Sin` remarks). v0.5.6 fixed Lua using the C# default locale instead of the invariant one (PR #314, [v0.5.6 notes](https://github.com/nuskey8/Lua-CSharp/releases/tag/v0.5.6)). GC-dependent behaviour: no weak-table or finalizer claims found in the README; unmeasured.

Interop cost. `[LuaObject]` partial classes with `[LuaMember]`/`[LuaMetamethod]` get generated glue at compile time (README "LuaObject"); unsupported member types are a compile-time error. Hand-written `LuaFunction` lambdas read arguments from a context with `GetArgument<T>` and write returns with `context.Return` (README "Calling C# Functions from Lua"), and a stack-based `CallAsync` overload avoids argument arrays. All entry points return `ValueTask`; v0.5.6 and v0.5.7 applied a light `ValueTask` builder to internals and fixed its allocation (PRs #330, #339). The project's own benchmark image ([docs/Benchmark.png](https://github.com/nuskey8/Lua-CSharp/blob/main/docs/Benchmark.png), last changed 2024-10-14, so it predates the 0.5.0 VM rewrite) reports "Calling C# function 25,000 times": NLua 36.45 ms / 12,306.5 KB allocated, MoonSharp 19.87 ms / 13,887 KB, Lua-CSharp 8.05 ms / 31.3 KB. It is a vendor benchmark with no stated machine or versions; treat it as a direction, not a number.

Godot. Pure managed assembly with no native assets, so nothing extra has to be loaded from the Godot export. The source generator runs when `Sky.Scripting` builds, not in the Godot project. Unverified in Godot 4.7 by this project.

License. MIT ([LICENSE](https://github.com/nuskey8/Lua-CSharp/blob/main/LICENSE); nuspec `<license type="expression">MIT</license>`).

### 2. MoonSharp

Maintenance. Repo [moonsharp-devs/moonsharp](https://github.com/moonsharp-devs/moonsharp), 1,617 stars, last push 2026-08-04, last commit 2026-07-30 ("fix: multiple assignment lost values passed to __newindex", Max Hayman). The stable line stopped at [v2.0.0.0](https://github.com/moonsharp-devs/moonsharp/releases/tag/v2.0.0.0) (2016-10-14); [v3.0.0-beta.1](https://github.com/moonsharp-devs/moonsharp/releases/tag/v3.0.0-beta.1) was published on GitHub 2026-03-03, and the NuGet registration shows `3.0.0-beta.1` published 2026-07-04 ([nuget.org/packages/MoonSharp](https://www.nuget.org/packages/MoonSharp)). Between 2025-01-01 and 2025-12-31 there were no commits; since 2026-01-01 there are 58 commits from 16 authors (Max Hayman, Benjamin Dobell, Kelly Birr and others). Historical top contributor is xanathar (310 commits), then Benjamin-Dobell (39). 92 open issues, 20 open PRs, 4 PRs merged since 2026-03-26. The 3.0 beta notes are about dropping .NET < 4.5, JSON empty-array tokens and debugger work, not the VM.

Platform. The 3.0.0-beta.1 package holds `lib/net45` and `lib/netstandard2.0` only (nupkg contents; `MoonSharp.Interpreter.csproj` has `<TargetFrameworks>netstandard2.0;net45</TargetFrameworks>`, [csproj](https://github.com/moonsharp-devs/moonsharp/blob/master/src/MoonSharp.Interpreter/MoonSharp.Interpreter.csproj)). A netstandard2.0 library loads on net10.0; behaviour on .NET 10 is unmeasured. No native binaries.

Language. "99% compatible with Lua 5.2 (with the only unsupported feature being weak tables support)" ([README](https://github.com/moonsharp-devs/moonsharp/blob/master/README.md)). Numbers are doubles (5.2). `goto` is implemented (`Tree/Statements/GotoStatement.cs`, `LabelStatement.cs`, tests in `EndToEnd/GotoTests.cs`). Coroutines are supported, including as C# iterators (README). Strings are Unicode and GC is the .NET GC ([moonluadifferences](https://www.moonsharp.org/moonluadifferences.html)).

Sandboxing. `CoreModules` flags choose modules; `Preset_HardSandbox = GlobalConsts | TableIterators | String | Table | Basic | Math | Bit32`, `Preset_SoftSandbox` adds metatables, error handling, coroutines, `OS_Time`, dynamic and JSON, and only `Preset_Default` adds `LoadMethods`, `OS_System` and `IO` ([CoreModules.cs](https://github.com/moonsharp-devs/moonsharp/blob/master/src/MoonSharp.Interpreter/Modules/CoreModules.cs) lines 19-103). So a script with no io, os system, load/loadstring/dofile or debug is a constructor argument. Each `Script` has its own globals, and `loadsafe` defaults to the current `_ENV` "for easier sandboxing" ([moonluadifferences](https://www.moonsharp.org/moonluadifferences.html)). Instruction limit: `Coroutine.AutoYieldCounter` forces a yield after N instructions, but only when `m_CanYield` and the state is not `Main` ([Processor_InstructionLoop.cs](https://github.com/moonsharp-devs/moonsharp/blob/master/src/MoonSharp.Interpreter/Execution/VM/Processor/Processor_InstructionLoop.cs) lines 14-43), so a budget needs the script run inside a coroutine and the host to count forced yields; it cannot pre-empt across a C# callback. No memory limit. Errors are exceptions ("Easy to use error handling (script errors are exceptions)", README).

Determinism. `math.random` uses a `new Random()` stored in the script registry ([MathModule.cs](https://github.com/moonsharp-devs/moonsharp/blob/master/src/MoonSharp.Interpreter/CoreLib/MathModule.cs) lines 20-35), so it must be replaced with an engine-seeded function. `Table` keeps its pairs in a `LinkedList<TablePair>` indexed by dictionaries ([Table.cs](https://github.com/moonsharp-devs/moonsharp/blob/master/src/MoonSharp.Interpreter/DataTypes/Table.cs) lines 12-31), so `pairs` follows insertion order (read from source, unmeasured). Transcendentals go through `System.Math` with the same CRT caveat as Lua-CSharp.

Interop cost. CLR types are registered as userdata; `InteropAccessMode` is `Reflection`, `LazyOptimized`, `Preoptimized`, `BackgroundOptimized`, `Hardwired`, `HideMembers` or `NoReflectionAllowed`, and the mode is a hint that MoonSharp may downgrade to `Reflection`, "particularly ... on AOT platforms like iOS" ([InteropAccessMode.cs](https://github.com/moonsharp-devs/moonsharp/blob/master/src/MoonSharp.Interpreter/Interop/InteropAccessMode.cs)). The optimized modes compile expression trees in the reflection member descriptors (`PropertyMemberDescriptor.cs`, `FieldMemberDescriptor.cs`, `MethodMemberDescriptor.cs` match `Expression.Lambda` in a GitHub code search). `MoonSharp.Hardwire` generates descriptors ahead of time. The only published figure found is Lua-CSharp's 2024 chart above (19.87 ms and 13,887 KB for 25,000 C# calls); the repo has a `DevTools/PerformanceComparison` project but no published results. The project's own rationale is "to sacrifice Lua raw execution speed in order to gain performance on Lua/C# cross calls" ([moonluadifferences](https://www.moonsharp.org/moonluadifferences.html)).

AOT, trimming, Godot. Reflection interop is not trim-annotated (unmeasured; expect trimming warnings if `Sky.Scripting` is trimmed). It detects AOT at runtime ([PlatformAutoDetector.cs](https://github.com/moonsharp-devs/moonsharp/blob/master/src/MoonSharp.Interpreter/Platforms/PlatformAutoDetector.cs)). Pure managed, so no native loading in Godot.

License. BSD 3-clause, "Copyright (c) 2014-2016, Marco Mastropaolo", with KopiLua-derived string library parts ([LICENSE in the nupkg](https://www.nuget.org/packages/MoonSharp); README "License"). BSD-3-Clause is permissive and compatible with an MIT repo; binary redistribution must reproduce the notice, so it goes in `CREDITS.md`.

Fork: [wallstop/NovaSharp](https://github.com/wallstop/NovaSharp) is a MoonSharp port targeting "Lua 5.4.8 semantics" and netstandard2.1, created 2025-11-08, 55 commits in 2026 (last push 2026-09-24), 3 stars, no GitHub releases, and its NuGet id `WallstopStudios.NovaSharp.Interpreter` returns 404 on nuget.org and has no registration. Its README shows an MIT badge but says "released under a 3-clause BSD license"; the GitHub API reports the license as NOASSERTION. Watch, do not adopt.

### 3. KeraLua (native Lua 5.4 via P/Invoke)

Maintenance. Repo [NLua/KeraLua](https://github.com/NLua/KeraLua), MIT, 376 stars, [v1.4.10](https://github.com/NLua/KeraLua/releases/tag/v1.4.10) on 2026-09-12; 2026-09-01 commit "Bump Lua 5.4.9 + Bump net9 mobile to net10". Effectively one maintainer: viniciusjarina has 381 of the commits, and 2026's 15 commits come from him and one contributor. 9 open issues, 2 open PRs. The Lua sources are the submodule [NLua/lua](https://github.com/NLua/lua) (last commits 2026-09-01, "Bump Lua 5.4.9").

Platform. The 1.4.10 nupkg contains `lib/net8.0`, `lib/netstandard2.0`, `lib/net46` and net10.0 mobile TFMs, and native `runtimes/win-x64/native/lua54.dll`, `runtimes/linux-x64/native/liblua54.so`, plus win-x86/arm/arm64, linux-arm64, osx, android, ios, tvos and maccatalyst ([nuget.org/packages/KeraLua](https://www.nuget.org/packages/KeraLua)). A net10.0 desktop app resolves `lib/net8.0`. Imports are `[DllImport("lua54", CallingConvention.Cdecl)]` ([NativeMethods.cs](https://github.com/NLua/KeraLua/blob/main/src/NativeMethods.cs) lines 27-44).

Language. Lua 5.4.9: int64/double subtype, `goto`, coroutines, `<const>`/`<close>`, full standard library.

Sandboxing. `new Lua(openLibs: false)` plus per-library `luaopen_base`, `luaopen_table`, `luaopen_coroutine` and so on ([Lua.cs](https://github.com/NLua/KeraLua/blob/main/src/Lua.cs) lines 43-50 and ~2009-2034). Per-script `_ENV` tables via `load` with an env argument. Instruction limit: `SetHook(LuaHookFunction, LuaHookMask, int count)` wraps `lua_sethook` (Lua.cs line 1169). Memory limit: `new Lua(LuaAlloc allocator, IntPtr ud)` and `SetAllocFunction` (Lua.cs lines 62, 1146) allow a capped allocator. Errors: `lua_pcall` status codes; but `lua_error` is a C `longjmp` (the library is built as C: `LINKER_LANGUAGE C` in [CMakeLists.txt](https://github.com/NLua/lua/blob/main/CMakeLists.txt) line 143), and Microsoft says "Interop with setjmp and longjmp C functions is not supported. You can't use longjmp to skip over managed frames" and that unmanaged exception interop "is supported on Windows platforms only" ([Exceptions interoperability](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/exceptions-interoperability)). Raising a Lua error from inside a C# callback therefore jumps over managed frames. NLua issue [#344](https://github.com/NLua/NLua/issues/344) ("Segmentation Fault caused by uncatchable exception", open since 2020-01-08, Linux only) and [#560](https://github.com/NLua/NLua/issues/560) (open, 2026-03-12: `error('test')` crashes on Alpine, works on Windows; that report used the system `lua5.4`, not KeraLua's build) show the effect. The mitigation (PR [#478](https://github.com/NLua/NLua/pull/478), open since 2023-02-05) is to return errors from C# callbacks and raise them from a Lua-side wrapper.

Determinism. Lua 5.4 seeds its string hash per state: `luai_makeseed` mixes `time(NULL)`, the state address, a stack address and `&lua_newstate` "Rely on Address Space Layout Randomization (if present) and current time" ([lstate.c](https://github.com/NLua/lua/blob/main/src/lstate.c) lines 55-80, used at line 388). `pairs` order over string keys therefore differs between runs, and table/userdata keys hash by address. Keeping it reproducible needs either sorted iteration in every script or a native build that defines `luai_makeseed` to a constant, which means shipping our own binaries. `math.random` is xoshiro seeded from `time(NULL)` and the state address when unseeded ([lmathlib.c](https://github.com/NLua/lua/blob/main/src/lmathlib.c) lines 628-632); replace it. Floats use the platform C libm (MSVC on Windows, glibc on Linux), so transcendentals may differ between the Windows client and Linux CI (unmeasured). GC is incremental/generational and address-dependent; weak tables and `__gc` timing would vary (unmeasured).

Interop cost. Raw KeraLua has no object bridge: C# functions are `LuaFunction` delegates marshalled to function pointers, and values move through the Lua stack by hand. Each Lua-to-C# call is a reverse P/Invoke transition. Unmeasured; no published KeraLua-only benchmark found.

AOT, trimming, Godot. `DllImport` with blittable signatures is usable under NativeAOT, but delegate marshalling needs the delegates kept alive (unmeasured here). Godot 4 exports C# through `dotnet publish`, and a Godot maintainer says "if you reference a NuGet package that includes native libraries, those native libraries should be included" when they sit in `runtimes/{rid}/native` ([godot-proposals discussion #13025](https://github.com/godotengine/godot-proposals/discussions/13025)); issue [#22787](https://github.com/godotengine/godot/issues/22787) was marked fixed in 4.0 "tho in some cases the native libraries may still fail to load anyways". Issue [#61404](https://github.com/godotengine/godot/issues/61404) is still open, and a 2026-02-26 comment there hypothesises that Godot's `PluginLoadContext` loses the native search path in the editor, with `NativeLibrary.SetDllImportResolver` as the workaround used by Steamworks.NET. NLua's [#451](https://github.com/NLua/NLua/issues/451) ("Request support for godot", open) reports macOS needing a custom library name.

License. MIT (KeraLua) and MIT (Lua).

### 4. NLua (reflection bridge on KeraLua)

Maintenance. [NLua/NLua](https://github.com/NLua/NLua), MIT, 2,246 stars, [v1.7.9](https://github.com/NLua/NLua/releases/tag/v1.7.9) 2026-05-01 (depends on KeraLua 1.4.9 per its nuspec), last commit 2026-09-13. Same single maintainer as KeraLua (viniciusjarina, 514 commits); 12 commits in 2026 from 2 authors. 105 open issues, 7 open PRs, 1 PR merged in six months.

Everything under KeraLua applies, plus: `Init()` always creates a `luanet` global and runs a bootstrap that calls `luanet.load_assembly('mscorlib')`, and `ObjectTranslator` registers globals `import_type`, `load_assembly`, `make_object`, `free_object`, `get_method_bysig`, `get_constructor_bysig`, `ctype` and `enum` ([Lua.cs](https://github.com/NLua/NLua/blob/main/src/Lua.cs) lines 65 and 278-328, [ObjectTranslator.cs](https://github.com/NLua/NLua/blob/main/src/ObjectTranslator.cs) lines 164-185). A sandbox must strip all of these and never hand scripts a raw CLR object, since members are resolved by reflection. Issue [#544](https://github.com/NLua/NLua/issues/544) (open) reports a C# argument-conversion exception in a method call escaping the host's `try/catch`. AOT: [#500](https://github.com/NLua/NLua/issues/500) and [#530](https://github.com/NLua/NLua/issues/530) report members missing under NativeAOT; trimming: [#556](https://github.com/NLua/NLua/issues/556) (IL2104, open). `SetDebugHook(LuaHookMask, int count)` exists (Lua.cs line 963). The 2024 Lua-CSharp chart puts NLua at 36.45 ms and 12,306.5 KB for 25,000 C# calls. Not recommended.

### 5. NeoLua

[neolithos/neolua](https://github.com/neolithos/neolua), Apache-2.0, 502 stars. NuGet description: "A Lua implementation for the Dynamic Language Runtime (DLR) ... Currently the implementation is on the level of Lua 5.3" ([nuget.org/packages/NeoLua](https://www.nuget.org/packages/NeoLua)). 1.3.19 on 2025-12-04, 1.3.20-beta.1 on 2026-01-15; a 2026-01-14 commit fixed "issue on .net 10" (#197); last commit 2026-03-27; one main author (neolithos, 387 commits). It compiles Lua to expression trees on the DLR and depends on `Microsoft.CSharp`, so it needs runtime code generation and is a poor fit for trimming or AOT. Not evaluated further.

### 6. Newer native wrappers (watch list)

- [nuskey8/NuLua](https://github.com/nuskey8/NuLua): "Unified Lua5.x/LuaJIT/Luau bindings for .NET and Unity", MIT, by the Lua-CSharp author. Created 2026-06-14, v0.1.0 on 2026-06-22, no commits since 2026-06-22, one committer. README: "This library is currently provided as a preview." `NuLua.Runtime.Lua54` 0.1.0 depends on per-RID packages including `win-x64` and `linux-x64`; TFMs `net10.0`, `net11.0`, `netstandard2.1`. It has `SetHook`, but "SetHook() is not supported in Luau". Interesting because Luau is designed for sandboxing, but too new for M0.
- [tilkinsc/Lua.NET](https://github.com/tilkinsc/Lua.NET): MIT bindings for Lua 5.0 to 5.4.7 and LuaJIT, last release v6.0.1 (2025-01-20), last push 2025-11-23, one main author. Low-level only.
- [spxnso/LuauInterop](https://github.com/spxnso/LuauInterop): MIT Luau bindings, v1.2.1 on 2026-08-10, 11 stars.

## Questions only the spike can answer

- Does either managed runtime keep 200 passengers with about 10 activities inside the 64x budget (256 ticks a second at 250 ms ticks), first when Lua runs only at decision points and then when it runs every tick, compared with plain C# scoring?
- What does one C#-to-Lua call cost on each, in time and bytes allocated, on .NET 10 on the owner's machine, with the interop style we would really use (Lua-CSharp `[LuaObject]` adapters versus MoonSharp registered or hardwired userdata)?
- Is Lua-CSharp's `ValueTask` API allocation-free on the synchronous path in a tight host loop, as the 0.5.6/0.5.7 builder changes suggest?
- How much does an instruction budget cost in practice: Lua-CSharp's count hook at a realistic count (issue #338 measured 3.16x at `count = 4`), and MoonSharp's `AutoYieldCounter` with scripts run as coroutines? Can the budget be charged only at decision points so the per-tick path pays nothing?
- With `math.random` replaced and inputs fixed, do two runs from the same seed produce byte-identical journals on each runtime, on Windows and on Linux CI (including any `math.sin`/`math.exp` a script uses)?
- Does `pairs` order match between runs and between Windows and Linux, as the source reading predicts for both managed runtimes?
- Does a throwing script get caught per definition and leave the state usable on both runtimes, including errors raised inside C# adapter callbacks and deep recursion (Lua-CSharp #168)?
- Does the chosen runtime load and run from `Sky.Scripting` inside the Godot 4.7.2 .NET editor and an exported Windows build, and does `Sky.Scripting` build cleanly with trimming analysis enabled (zero-warnings policy)?
- Does Lua 5.2 (no integer subtype, no bitwise operators) limit anything the content design needs, or is double-only arithmetic acceptable for event scripts?
- Only if both managed runtimes miss the budget: what does KeraLua gain, and what does it cost to ship our own native build with a fixed `luai_makeseed` and error handling that never longjmps over managed frames?
