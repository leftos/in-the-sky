# M1: the headless cabin flight

**Goal.** `Sky.Sim` flies one narrowbody reference flight from a seed with no Godot: about 180 passengers from a seeded manifest and 6 crew, boarding through cruise service to deboarding, with crew auto-resolving a few new Lua events, and ends with a score and a text report. The same seed and journal replay it exactly, invariant fuzzing runs over 500 seeds, and a performance test pins 64x at full cabin. **Acceptance** is the list in [CONCEPT.md section 7](../design/CONCEPT.md#7-m1-definition-of-done); every item there maps to a step below (the table at the end). **Out of scope** (M2 and later): the Godot client and anything drawn, the dev inspector UI (M1 only records and dumps decision scores), the display RNG's first use, player commands and journaled command records, the player HUD and staffing as a player lever, the widebody, voice and the small model, SimConnect and the MSFS feed, the layout editor and layout `extends`/`overrides`, saves, AirlineOps. Scope comes from section 1 of [the decisions doc](./2026-09-26-rewrite-decisions.md); terms are in the glossary in [docs/README.md](../README.md).

## How to read this plan

Steps are in working order, grouped into waves by the files they touch. Waves with disjoint files run side by side; inside a wave, a step that consumes another waits for it. Each step names what it consumes (`needs`), the files it owns, and its proving command in the wrapped form, with the new test that must fail first. A step is one implementer brief unless a **Brief** line pairs it with another (a brief holds about four steps or six files at most). The orchestrator updates `docs/ARCHITECTURE.md` (the layer's section and the task index), `docs/TEST_ALMANAC.md` (a row per new class, the counts) and the glossary in the same commit as each step (ruling R25). The design docs `docs/design/passengers.md`, `crew.md` and `events.md` add requirements to later steps by name (B1's crew stations and jumpseats, B3's crew and passenger squeeze states, E2's claim against hold priority, S3's consequence kinds, F5's need reads and reading lights, F6's notice-based resolution and waiting limit, K1's empathy field); a brief for any step reads those docs' mentions of it first. Design-doc steps name the studio agent that owns them; the `OD` decisions they consume are ruled under "Owner decisions" at the foot.

Start order: waves M1-D, M1-A, M1-B, M1-C, M1-E and M1-S have disjoint files and nothing in common, so all six start at once. M1-K follows B and C; M1-F follows A, B, C, E and the port files of S; M1-G's calculators run beside F; M1-X (content data) runs beside F once D and K land; M1-H, M1-I and M1-Z close.

## Rulings

Technical choices settled here so no implementer has to make them. Each cites its source.

- **R1. The edges stay as they are; `Sky.Sim` uses only `Sky.Session`'s API.** `tests/Sky.Sim.Tests/ReferenceTests.cs` pins `expected = ["Sky.Session"]`, and the `docs/ARCHITECTURE.md` table gives `Sky.Sim` → `Sky.Session` only. Using an Engine type from Sim would add `Sky.Engine` to Sim's metadata and fail that test, so Session exposes `FlightResult`, the report text, the journal and the CSV row fields as its own types, and Sim stays a thin command line.
- **R2. The Engine does no IO and holds no package.** ADR 0001 (`docs/decisions/0001-the-engine-references-nothing.md`): "no Godot, no Lua runtime, no IO". Ports live in `src/Sky.Engine/Ports/`; the journal is in-memory records in the Engine, and `Sky.Session` reads and writes the file.
- **R3. Forbidden APIs are caught by an IL-reading test, not an analyzer package.** ADR 0001 forbids package references in `Sky.Engine`, which rules out `BannedApiAnalyzers`; ADR 0002 and 0003 name what must not appear (wall clock, Stopwatch budgets, unseeded `Random`). `System.Reflection.Metadata` is part of the runtime, so the test (A3) adds no dependency.
- **R4. The tick is 250 ms; sim time is a tick index.** ADR 0010 (`docs/decisions/0010-lua-csharp-at-decision-points-and-250-ms-ticks.md`): "The tick stays at 250 ms". Rates are per sim hour in content (decisions doc section 1, "need rates per sim hour") and turned into per-tick deltas at load. Accumulated time carries its remainder (decisions doc section 3: "About 54 accumulators reset to zero and drop their overshoot").
- **R5. Random numbers come from the project's own generator, not `System.Random`.** ADR 0010 Open: "Seeded System.Random output across .NET major versions is not checked here; the journal format should not rely on it". ADR 0003: one seeded root with named streams. Each stream is xoshiro256** seeded through SplitMix64 from the root seed and the FNV-1a-64 hash of its name (never `string.GetHashCode`, which is randomized per process). Stream names: `manifest`, `feed`, `events`, `passenger/<id>`, `crew/<id>`. Amended at A2 (orchestrator, 2026-09-26, from review): the SplitMix64 seed is FNV-1a-64 over the root seed's 8 bytes little-endian followed by the name's UTF-8 bytes (an XOR of the two made seed 1's `passenger/0` equal seed 1099511628274's `passenger/1`), and `NextInt(max)` is the high 64 bits of a 64 × 64 multiply.
- **R6. Determinism rules for sim code.** From the spike (`docs/research/2026-09-26-lua-boundary-spike/README.md`): identical hashes held when scripts used only `+ - * /`, comparisons and the host `math.random`, and "no `math.sin`, `math.exp` or other transcendental was exercised"; `pairs` order differs between runtimes and is unmeasured across OSes. So: sim state is iterated in id order over arrays and lists, never over a `Dictionary` or `HashSet`; a flight runs on one thread (sweeps parallelize across seeds only); transcendental functions (`Math.Pow`, `Math.Exp`) run only at load to build per-tick constants; Lua content uses `ipairs`, never `pairs`, for anything that changes an outcome.
- **R7. The Lua host is exactly the measured one.** ADR 0010: Lua-CSharp, an instruction budget through the count hook, stack restored after a caught error, an overflowed state discarded, `math.random` replaced, no global table. The package is `LuaCSharp` 0.5.7, the version the spike measured (spike README, Machine table); an upgrade is its own change that re-runs Z2. The sandbox whitelist is the spike's: `assert`, `error`, `ipairs`, `next`, `pairs`, `pcall`, `select`, `tonumber`, `tostring`, `type`, `xpcall`, and copies of `string`, `table` and `math` with `random` replaced and `randomseed` removed. The budget is the spike's hook: count 1,000, disabled after 1,000 fires in one call. One `LuaState` per flight; each module in its own environment table.
- **R8. Lua runs only at decision points.** ADR 0010: "when a character chooses its next activity, and when an event's `trigger`, `describe`, `choices` or `effects` is evaluated. Per-tick work (need rates, the rate rule, movement) is C#." Activities are Lua `utility` modules; traits, needs and layouts are JSON data.
- **R9. Content lives in `src/Sky.Content/Data/`, as JSON through one library, with ids as strings.** The M0 commit-msg check in `docs/plans/MAIN.md` wave M0-C ties `src/Sky.Content/` to `docs/design/`; the decisions doc section 3 lists "two JSON libraries" and "Traits as a C# enum" to avoid. So: `System.Text.Json` with a source-generated context (no reflection, in line with ADR 0010's trimming results), trait, profession, activity and event ids as content strings interned to integer ids at load, and `Data/**` copied to the output directory so tests and `Sky.Sim` load it from `AppContext.BaseDirectory`. The five needs are a C# enum, because CONCEPT section 8 question 1 fixes the set. Lua and JSON are not ledger assets (`assets/PROVENANCE.toml` header: "Lua, JSON and other authored content is MIT code, and not an asset").
- **R10. Load errors stop the load.** Decisions doc section 3: "Load errors are swallowed into empty dictionaries". Every loader and validator error names the file, the JSON path or module id, and what was expected.
- **R11. The journal is JSONL with a header, input records and outcome records.** ADR 0004 (`docs/decisions/0004-the-journal-and-exact-replay.md`): ticks per frame and every observation, so replay is exact. CONCEPT section 6: every cited moment carries "the tick it happened at so it can be found in the journal". The file is one JSON object per line, LF, doubles in round-trip form: a header (format version, seed, scenario id, content hash), input records (frame tick counts, feed observations) that replay consumes, and outcome records (moments) that replay regenerates and compares but never reads as input. M1 writes no command records (no player commands, decisions doc section 1).
- **R12. The end-state hash is SHA-256 over a canonical dump.** The spike's determinism mode hashed "every need's IEEE bits, every current activity and the tick count"; M1 adds node ids, the stage and the task board, in id order.
- **R13. Inches become ticks once.** ADR 0005 (`docs/decisions/0005-real-unit-layouts-and-a-derived-nav-graph.md`): "Simulation logic never reads inch positions; it works on the nav graph." The builder turns inches into per-edge traversal ticks; everything after uses the graph and the next-hop table. Rows are numbered from 0 at the front in the one coordinate space; seat letters are content labels only.
- **R14. A cart fills its aisle slot and cannot be squeezed past.** CONCEPT section 2, pillar 3's canonical story: "the queue blocks the cart". Other squeeze specifics are D2's.
- **R15. The rate rule is CONCEPT's formula with a 0.2 floor.** CONCEPT section 4 and section 8 question 2: `m = clamp(1 + Σ_class (Π_i m_i − 1), 0.2, 2.5)`.
- **R16. Decision records keep the top three candidates for every decision of the flight.** CONCEPT section 7: "A passenger decision records its top candidate scores, and a dump of them is readable for any passenger and tick." The spike counted about 2,700 decisions a flight, so keeping all of them in memory is small; the dump is `Sky.Sim decisions`.
- **R17. The stage machine checks its handler map and runs every crossed `Start`.** Decisions doc section 2: "whose factory map is checked for completeness at startup, which still runs each handler's `Start` when several stages are crossed in one frame".
- **R18. Standalone mode's feed is `FlightEmulator` in `Sky.Session`.** ADR 0001 has other projects implement the Engine's ports, and ADR 0004 journals every observation, so a replay reads the feed from the journal and never runs the emulator.
- **R19. Flight-level tests live in `tests/Sky.Session.Tests`; the suite fuzzes 16 seeds and the runner fuzzes 500.** `Sky.Session` is the lowest project that composes content, scripts and the Engine. `sky.ps1` gives every test module `--timeout 2m`, and `tools/test-all.ps1` gives the tests 180 s, so the 500-seed fuzz and the sweeps run through `sky.ps1 sim`, not the suite.
- **R20. The performance test runs in the default suite and asserts the requirement itself.** ADR 0010 measured 134,275 ticks/s with the budget on, 524x the 256 ticks/s target, so the assertion is the target (256 ticks/s over a whole full-cabin flight) with no machine-specific margin.
- **R21. A golden hash settles cross-platform replay.** ADR 0010 Open: "Byte-identical replay on Linux, and `pairs` order across Windows and Linux, are unmeasured. The M1 replay test runs in CI on Linux and settles them." `GoldenFlightTests` pins a hash recorded on Windows; a Linux-only failure is a finding to report to the orchestrator, not a hash to re-record.
- **R22. `Sky.Sim` parses its own arguments.** Five subcommands with a few switches each do not justify a new package (the user's standing rule on dependencies); a bad argument exits 2 with the usage line.
- **R23. `sky.ps1 sim` runs through the gate.** `sky.ps1` help: "Every gate - build, test, the formatters - runs through tools/gate.ps1 under a ceiling of its own". The runner is built Release, as the spike measured.
- **R24. The scenario carries system switches for needs, events and contagion.** CONCEPT section 2, pillar 6: "Every system can be switched off and the flight still runs". These are the three of pillar 6's list that exist in M1.
- **R25. Docs move with each step.** `docs/ARCHITECTURE.md` and `docs/TEST_ALMANAC.md` state that the doc-drift hook fails on an unnamed project or `*Tests` class, and the user's global rule puts every coined term in the glossary in the commit that first uses it. The orchestrator makes those edits in the step's commit.
- **R26. A content commit stages its design doc.** MAIN.md wave M0-C: "a commit staging `src/Sky.Content/` also stages `docs/design/` or carries `Docs: unchanged, <why>`".
- **R27. The event module shape.** Decisions doc section 2 and `.claude/agents/event-writer.md`: a module is declarative, with `trigger`, `describe`, `choices` and `effects`; effects return delayed consequences. The module returns a table `{ id, phases, trigger(ctx), describe(facts), choices(facts), effects(facts, choice_id) }`. `trigger` returns nil or a facts table; `choices` returns two to four `{ id, label, needs_crew, minutes, ... }` with the per-choice field OD1's ruling adds; `effects` returns a list of `{ after_minutes, target, need, delta }` or `{ after_minutes, target, incident }`. Targets are selectors the host resolves (`"subject"`, `"neighbours"`, a passenger id from the facts).
- **R28. Invariants are checked after every tick when asked for.** The fuzz and the tests turn the checker on; a plain `run` and the performance test leave it off, so the 64x figure measures the flight alone.
- **R29. The forbidden-API guard bans by namespace where the Engine has no use at all** (orchestrator, 2026-09-26, from A3's review). Banned: every type in `System.Threading`, `System.IO` (except the in-memory `TextWriter`, `TextReader`, `StringWriter`, `StringReader`), `System.Net` and `System.Security.Cryptography` and their sub-namespaces; `Random`, `Stopwatch`, `Process`, `Console`, `ParallelEnumerable`, `TimeProvider`, `HashCode`; `DateTime.Now`/`UtcNow`/`Today`, `DateTimeOffset.Now`/`UtcNow`, `Guid.NewGuid`/`CreateVersion7`, `String`/`StringComparer.GetHashCode`, and every `Environment` member but `NewLine`. Members of generic types are checked through their definition. Compiler-synthesized record hashes (`EqualityComparer<T>.GetHashCode`) stay allowed: R6 keeps hash order out of outcomes. A C# `event` or `lock` trips the ban (both compile to `System.Threading`), so the Engine uses neither, or argues an allowlist entry.
- **R30. The nav graph's shape** (orchestrator, 2026-09-26, B1 and B2). Node ids go row by row (aisle slots, then seats left to right), then fixtures in list order, a lav giving its queue node then itself. A fixture (door, lav, galley) sits beside the aisle slot of its row and aisle at a distance in inches; a lav's queue sits halfway. A seat group's end seat links only to the nearest aisle on each side with no group between; cross-aisle passages are twin-aisle work (M3). Ticks per edge are `max(1, ceil(round(inches / inchesPerTick, 9)))`. `PathTable` runs Dijkstra per target on ticks; the next hop is the lowest-id neighbour on a shortest path. crew.md's crew stations and jumpseats join as new fixture kinds.
- **R31. Occupancy is a capacity and legality table, not a mover** (orchestrator, 2026-09-26, B3). Capacity per node kind is a constructor input (`NodeCapacities`), since the lav queue and galley numbers are content's; a reservation and an arrival both count against it. A person reserving a full aisle slot that holds no cart and has not used its squeeze gets `Squeezed` (one over capacity); anywhere else a full node refuses. A cart reserves only an empty aisle slot, galley or door node (never a seat, lav or lav queue), and a node holding a cart admits nobody; carts take ids from the characters' `int` space and must not collide with one. The squeeze allowance is by count, not by flag: it is free again once a holder leaves (B3's review). Holders are the plain `int` character ids `Execution/` uses; `Release` frees a reservation or an arrival alike. The squeeze's extra ticks (crew.md's +4, a first value) are the mover's (F3), not Occupancy's.
- **R32. The layout ASCII line** (orchestrator, 2026-09-26, B4). One line per row, LF-joined with no trailing newline: the two-digit row index, a space, the row's seat groups and the cabin's aisles in lateral order (a group as its seat labels run together, an aisle as `|`), then for each fixture in that row, in layout list order, a space and its id. The two-row test layout renders `00 AC|DF door-1L lav-fwd` over `01 ABC|DEF galley-mid` when those are its fixtures' rows.
- **R33. The need set's shape** (orchestrator, 2026-09-26, C2). Values are `double`, 0 fine and 100 worst for all five. `NeedRates` is shared by the flight, built once from hourly settings, with the Unease pull factor `0.5^(1/half-life ticks)` precomputed (R6). `NeedSet` is per passenger, holding its Unease baseline. `Tick` takes one composed multiplier per need (the caller composes the modifiers through `RateMultiplier`) and a `NeedContext` (asleep, on IFE); the multiplier scales a need's base change this tick, Rest's fall included, and does not touch Unease's pull. Pulses are a queue that lands its remainder evenly over the remaining ticks, so a pulse lands whole. Amended by C3a (game-designer, 2026-09-26): the Unease multiplier scales each tick's positive pushes and leaves relief and the pull alone; Rest's multiplier scales only the rise while awake, and the fall asleep is the `sleep` rate. C2b makes the code match.
- **R34. The board arbitrates, the executor swaps** (orchestrator, 2026-09-26, E2 and E3). crew.md gives a task a claim and a hold priority, and the executor's single immutable `Priority` cannot serve both (the cart and the due galley break diverge in opposite directions), so `TaskBoard` compares a challenger's claim against the holder's hold itself and calls a new `SequenceExecutor.Replace`, which runs the running action's cleanup and installs the new one with no priority check. The board is zone-agnostic: the caller passes a `mayTake` predicate that carries zone, spill and seated rules (F5), and the tie after claim and age is the lower task id; nearest-by-path is F5's. `CrewNeeded` is carried, not enforced: a cart is two postings met at a sync point (F5). `CrewStrain` takes its numbers in one settings record, reads fatigue as a per-tick input (fatigue is `CrewMember`'s, F5), and counts ticks over the redline, reporting minutes at read time.

## Owner decisions

Ruled by the owner on 2026-09-26 from ranked options; each names the steps it unblocks and the worst case the owner accepted. The design rulings made while drafting D1, D2 and D4 (about thirty) live in the "Owner rulings" sections of `docs/design/passengers.md`, `crew.md` and `events.md`, not here.

1. **OD1. How crew auto-resolve an event's choice: weighted by quality.** Each choice carries an authored quality score for the facts the trigger saw; the crew member picks by weighted chance, with competence sharpening the weighting toward the best choice and fatigue and some traits flattening it toward even. Unblocks D2, D4, S3 (the per-choice field is `quality`), F6. Accepted worst case: resolution can read as a dice roll, and authors score every choice for every situation its trigger can see.
2. **OD2. The reference narrowbody: two classes, 180 seats.** 3 rows of 2-2 (12 seats) ahead of 28 rows of 3-3 (168), one lav forward and one aft, one galley aft, boarding and deboarding through the forward door. Unblocks D3, X1. Accepted worst case: "one lav locked" plays differently by lav, so the `one-lav-locked` variant names one (the aft lav) and the other goes unmeasured in M1.
3. **OD3. What a crew observation captures: visible behaviour plus revealed needs.** Where the passenger is, what they are doing (asleep, in the lav queue, eating), the call button and a distress band (calm, uneasy, distressed); and, when crew interact with the passenger (a call answered, a service pass, an event's crew task), the needs that interaction reveals. D1 names which interaction reveals which need. Unblocks D1, F5, H4. Accepted worst case: interaction-reveal rules are designed now for a view nobody reads until M3.
4. **OD4. The M1 scenario's levers: only the four section 7 tests.** The service plan (order, direction, start time), lavs open or locked, the lighting plan, and crew count with zone assignment; everything else is a fixed engine default. Unblocks D2, X2. Accepted worst case: the M3 levers join the schema later and their defaults shift the tuned baseline then.
5. **OD5. A seat-conflict event: yes, one.** One M1 event is a seat conflict (a split group or a swap request during boarding), auto-resolved like the rest. Unblocks D4. Accepted worst case: boarding slows on seeds where it fires, pushing cabin ready late on a few baseline seeds.
6. **OD6. Which sustained need failures raise an incident: every need.** Each of the five needs raises its own incident kind when it fails past its sustain window (Bladder an accident, Unease a panic, and D1 names the kinds for Refreshment, Rest and Boredom, such as a demand for food, a noise complaint, a disruptive passenger); fights still come from events. Unblocks D1, F6. Accepted worst case: five incident kinds on the baseline make "no missed incident on 90% of seeds" harder to reach, and D3 and Z7 tune thresholds and sustain windows so incidents stay exceptions (pillar 4).
